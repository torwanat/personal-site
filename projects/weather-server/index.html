Weather Server - secure backend for weather observations

A Java-based HTTPS server designed to receive, store, and manage weather observation data for a university Programming 3 assignment. The server exposes a small REST-like API over TLS, handles user registration and authentication, and persists data via a dedicated database layer.

Back to projects overview

Overview

The weather server is a backend-focused project that implements a secure HTTPS server listening on port 8001 and using a Java KeyStore (JKS) certificate for TLS. It provides endpoints for user registration, authenticated submission of weather data records, and management of collections of observations. The project follows the standard Maven project structure and builds on top of the Programming 3 course template.


  • Areas: Backend Development, Networking, Security, Java
  • Tech: Java, Maven, com.sun.net.httpserver, TLS/SSL, JKS, Logback/SLF4J
  • Status: Course project - source code available on GitHub

Tech stack and architecture

The project is implemented as a standalone Java application using the built-in com.sun.net.httpserver APIs to provide HTTPS endpoints. TLS is configured with a JKS keystore and standard javax.net.ssl components. The server exposes contexts for registration, data records, and collections, each handled by dedicated classes. A database layer encapsulates persistence for users, collections, and observation data, while Logback and SLF4J are used for structured logging.

Implementation details

The implementation focuses on correctly wiring HTTPS, authentication, and data handling in a clean Java architecture. Below are some of the key technical aspects of the project.


HTTPS configuration

At startup, the server loads a JKS keystore and initializes key and trust managers using standard Java security APIs. An SSLContext is configured and attached to the HttpsServer, ensuring all communication occurs over TLS. This required careful handling of keystore paths, passwords, and certificate loading, as well as robust error logging for common failure modes such as missing certificates or binding issues.


User authentication

The server uses a custom UserAuthenticatorDB to protect sensitive endpoints like /datarecord and /collections. Users are registered via a dedicated /registration context and stored in the database. Once registered, they must authenticate before they can submit or query weather observations or manage collections, enforcing a clear separation between public and protected functionality.


Database layer

The ServerDatabase class encapsulates all persistence logic for users, collections, and observation data. This separation keeps HTTP handling and business logic focused and makes it easier to change or extend the storage mechanism. The domain model, including the User class and observation-related classes in the observations package, reflects the core entities of the system.

What I learned

This project provided hands-on experience with building an HTTPS server in Java, including working with TLS, keystores, and low-level networking APIs. I gained a deeper understanding of authenticating users at the HTTP server level, structuring handler classes for different endpoints, and designing a small but cohesive domain and persistence layer. Additionally, the project improved my skills in error handling and logging for production-like backend services.
